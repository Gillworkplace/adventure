## 1. 结论

在固定设置后，于全新的 100,000 个种子上评估，v3 的平均最终 score 为 **1873.62695 分**。95% 置信区间为 **1872.37263 ~ 1874.88127 分**。相同种子下的 v2 为 **1863.82433 分**，配对改进量为 **+9.80262 分**，差值的 95% 置信区间为 **8.28441 ~ 11.32083 分**。

## 2. 本次策略的变化

v2 求解最多持有四张手牌的辅助问题，并用空手牌、单张、两张的价值来近似真实的五张手牌。v3 则**直接使用覆盖最多五张手牌全部组合的价值表**。

30 个卡片 ID 可按效果归并为 22 个类别。由于牌堆会重生成，可能重复持有相同效果或相同 ID 的卡片，因此允许重复组合。从空手牌到五张手牌的类别手牌数为 80,730 个，约为四张及以下（14,950 个）的 5.4 倍。

| 设置 | v2 | v3 |
|---|---|---|
| 辅助问题的手牌上限 | 4 | 5 |
| 真实手牌价值的表示方式 | 单卡与双卡交互的投影 | 直接查询 0~5 张手牌的价值 |
| 辅助问题规划 horizon | 24 次 | 24 次 |
| 在线期望值搜索 | 两层 | 一层 |
| 手牌价值总权重 | 0.975 | 1.0 |
| 牌堆修正系数 | 0.6 | 0.6 |
| 牌堆修正的抽牌率系数 | 0.7 | 0.7 |

该比较同时包含多项设计变更。不应把全部改进量解读为某一项变更的因果效应。

### 价值模型的范围

辅助价值表使用位置、剩余付费骰子次数、是否有奖励以及归一化的手牌。它处理与真实游戏手牌上限相同的五张牌，但**未来抽牌近似为对全部 30 张牌分布的 IID 有放回抽取**。它不是把整局游戏的 100 次全部完整求解的模型，而是在在线阶段使用 `min(剩余付费骰子, 24)` 的模型。

策略对每个合法行动的下一状态按概率对下列值求平均，并选择值最大的行动。

`辅助 DP5 价值 + 剩余牌堆的价值修正`

对于第一个行动，采用真实的骰子点数之和与对子的联合概率、落点、跳跃、获得卡片、不放回牌堆与牌堆重生成以及终局条件。若下一状态为终局状态，则不再叠加手牌价值与牌堆修正，只返回该位置本身的值。策略不接收未来随机数、游戏种子或牌堆的后续顺序。

牌堆修正与 v2 的形式相同。

`D_hat = 0.6 * min(1, 0.7 * (r + b) / deckCount) * sum(centeredCardValue[id])`

其中 r 是内部规划区间内剩余的付费骰子数，b 表示是否有奖励。卡片基准值沿用了 v2 所使用的中心化系数。抽走只剩一张的牌堆之后牌堆会重生成回完整牌堆，这一效果也有所反映。该项只是修正项，并不是以实际牌堆为条件的最优值本身。

因此，即便第一个行动的概率计算与手牌表查询完全准确，包含其后的 IID 近似、有限 horizon 与牌堆修正在内的策略，也并不是原始游戏的全局最优策略。

## 3. 计算器与存储方式

当前会话保留的附件中没有此前的五张 horizon 12 检查点。通过复用并改进原有计算器源码重新进行了计算，**完成了五张模型到 horizon 24**。并不声称制作了五张 horizon 32 或 horizon 48 的完整模型。另外单独计算的 horizon 48 模型是四张模型。

计算过程中使用两个奖励状态的价值层，以及抽牌期望值和骰子期望值缓冲区。对同一被移除手牌的多骰计算进行复用，并在手牌维度上做了向量化。不消耗付费骰子的卡片连锁，则在同一资源区间内以重复计算处理。

研究过程中，在完成 horizon 2 之后切换到了将抽牌计算向量化的实现。切换时**从已存储的 1/32 步长量化值重启过一次**。随后的 horizon 3~24 接续了重启后的计算。为了不隐藏这段历史，重生成脚本同样采用 `0~2 计算 → 头部扩展 → 从 horizon 2 恢复` 的相同流程。

存储文件按手牌大小分开保存。空手牌用 float32 存储，其余手牌则以相对空手牌的差值按 1/32 步长的 int16 存储。名义上单个值的存储舍入误差最大为 1/64 分。这并不意味着辅助问题的收敛误差或相对真实游戏的全部近似误差都被限制在 1/64 以内。

运行所需的六个 tier 文件总大小为 **23,403,917,092 字节，约 23.404GB**。研究用的双卡投影文件另计。计算在内存限制 4GiB、CPU 分配 4 核的环境下进行，计算器的工作内存约为 3.2GB。

## 5. 最终评估流程与评估器变更

基础种子库为 3809081000，第 i 局游戏的种子由 `mix(baseSeed + i)` 生成。每局游戏保持与原始版本相同的单一 Mulberry32 随机数流。为骰子和卡片分配独立随机数流的早期开发实验没有混入最终结果。

策略设置与样本数已先行记录。最终评估过程中唯一更改的是**游戏执行顺序**。为了降低完整价值表的 I/O 开销，将多局游戏按剩余付费骰子数交错执行。每局游戏保持独立的状态和 RNG，分数与行动记录仍按游戏顺序输出。

在更改前后分别与原始 JavaScript 引擎的 1,024 局对照，确认所有游戏的 score、行动数以及整体行动与分数哈希一致后，对固定的 100,000 个种子全部重新评估。此前中断运行的部分记录没有加入最终样本。样本数没有为了迎合分数而增减。

平均值的置信区间对按游戏计的样本标准误乘以 1.96；策略差异则对相同种子下的分数差值应用同样的计算。这是针对仿真样本的统计估计，不是对期望值的数学证明。

依据：`results/final-evaluation-plan.json`、`results/final-scheduler-amendment.json`，以及原始 CSV 和验证 JSON。

## 8. 产出物与运行

### 主策略 v3

研究包包含原始引擎、C++ 策略、Node.js 桥接、模型计算器、评估器、验证代码及结果。**23.4GB 的完整运行价值表未包含在 ZIP 中。**仅靠检查点也无法直接运行该 agent。需要所提供的重生成流程，或完全相同的完整 tier 文件。

```bash
bash research/build.sh
bash research/build-model.sh 4
node demo.js
```

重生成流程从空的模型目录开始，并体现了在 horizon 2 处经一次量化重启的实验历史。完成后与所提供的完整文件 SHA-256 对照。构建需要支持 C++17/OpenMP 的编译器和 Python 3。本研究使用的编译器是 g++ 14.2.0。Node.js 运行路径不安装任何 npm 包。实验用回归分析代码另行使用 NumPy。

主策略的接口是异步的。

```js
while (!board.terminal) {
  board.step(await agent.choose(board));
}
```

返回值为 0 或当前手牌的 1-based 槽位。v3 是使用原生 worker 的 Node.js agent，不是可在浏览器中独立运行的策略。

### 独立 horizon 48 候选

解压包含运行模型的 ZIP 并执行 `node demo.js`。该策略与既有版本一样使用同步式 `agent.choose(board)` 接口。通过该 ZIP 得到的策略性能是上述 20,000 局候选的结果，而不是 v3 的 1873.62695 分。

### horizon 24 检查点

按顺序还原两个 gzip 文件即可得到 horizon 24 的两个奖励层。压缩前大小为 936,168,296 字节。将存储的量化值**共 468,072,540 个**全部与原始存储值比对，确认了压缩与还原无损，并通过了后续计算器加载器的读取检查。

```bash
bash research/restore-checkpoint.sh PART1.qdelta.gz PART2.qdelta.gz model/h24.qdelta
```

该检查点用于续算此后的 horizon。它不是包含 horizon 0~23 完整价值表的运行模型，也不意味着本次完成了 horizon 25 及以上的计算。验证时只运行了加载器，没有计算后续层。检查点的无损压缩与上文所述价值表自身的量化误差需要区分看待。

## 9. 剩余研究课题

距离 1880 的当前差距为 **6.37305 分**。下一阶段实验的优先方向是：五张模型更长的规划区间、反映真实不放回牌堆的长期价值修正，以及在新批量执行器上进行选择性附加搜索。尚未验证哪种方法能带来多大改进。

以降低运行开销为目标的压缩与蒸馏同样重要。本次没有直接采纳基于线性回归的缩减候选。今后的缩减模型不能只评估数值的平均误差，还应同时评估实际行动选择与独立游戏的 score。

如果今后将这批 100,000 局种子库用于调参，那么其后候选的最终评估需要另用一批种子库。**新确立的基线是 1873.62695 分，1880 目标仍未达成。**
